## When to use me

Use this skill when the user pastes an axe-core violation report (JSON) into the chat and asks to fix it, such as "here are my accessibility violations — can you fix them?", "I have these axe-core errors", or "help me resolve these WCAG issues". This skill does NOT run the tests — it works from a user-provided violation report.

## Input format

The user pastes the `violations` array from `results.violations` returned by `@axe-core/playwright`. Expected structure (array of violation objects):

```json
[
  {
    "id": "color-contrast",
    "impact": "serious",
    "nodes": [
      {
        "html": "<span>Back to posts</span>",
        "target": [".mb-8 > span"],
        "any": [
          {
            "data": {
              "fgColor": "#98989a",
              "bgColor": "#ffffff",
              "contrastRatio": 2.87,
              "expectedContrastRatio": "4.5:1",
              "fontSize": "10.5pt (14px)",
              "fontWeight": "normal"
            },
            "message": "Element has insufficient color contrast of 2.87..."
          }
        ],
        "failureSummary": "Fix any of the following: ...",
        "impact": "serious"
      }
    ],
    "tags": ["cat.color", "wcag2aa", "wcag143"]
  }
]
```

The skill processes one violation at a time (each object in the array). If multiple violations are provided, process each independently and produce a combined report.

## Workflow

For each violation object:

1. **Parse** — Extract rule `id`, `impact`, `nodes` (element HTML, target selector, violation data)
2. **Locate** — Search the codebase using the element's HTML text content and/or CSS selector to find the exact file and line number
3. **Analyze** — Determine the root cause (CSS variable, missing attribute, incorrect hierarchy, etc.)
4. **Plan** — Construct a concrete, minimal fix
5. **Output** — Format as a structured markdown report

## Violation handlers

### 1. color-contrast

**Parse step — relevant fields:**
- `nodes[].any[].data.fgColor` — foreground color hex
- `nodes[].any[].data.bgColor` — background color hex
- `nodes[].any[].data.contrastRatio` — measured ratio
- `nodes[].any[].data.expectedContrastRatio` — required ratio (e.g. "4.5:1")
- `nodes[].any[].data.fontSize` — e.g. "10.5pt (14px)"
- `nodes[].any[].data.fontWeight` — e.g. "normal" or "bold"
- `nodes[].html` — the offending element's outer HTML
- `nodes[].target` — CSS selector array

**Locate strategy:**
1. Search for the text content inside the HTML string (e.g. `"Back to posts"`) across `.tsx`, `.ts`, `.mdx` files
2. If not found by text, search by unique class combinations from the `target` selector
3. If the element is generated by MDX content, search in `content/` directory `.mdx` files
4. Return the file path, line number, and surrounding code context

**Analyze strategy:**
1. Read the matched line to identify the Tailwind text color class (e.g. `text-muted-foreground`)
2. Trace the class through `tailwind.config.ts` to find the CSS variable reference
3. Read `app/globals.css` to find the variable definition in both `:root` (light) and `.dark` blocks
4. Compute the target lightness: for normal text (&lt;24pt) on white background, target ≥4.5:1. Reduce the `L` (lightness) value in the HSL variable until the contrast ratio would pass. Approximate: each 1% reduction in L increases contrast by ~0.4:1 against white
5. **Dark mode check** — After determining the fix for `:root`, verify that the `.dark` block's `--muted-foreground` value still maintains ≥4.5:1 against its `--background`. If the dark mode value would also be affected (shared variable), include a note about dark mode impact

**Fix format:**
```diff
- --muted-foreground: 240 2% 35%;
+ --muted-foreground: 240 3% 24%;
```

If the color is applied via an inline class (not a CSS variable), suggest changing the Tailwind class directly:
```diff
- className='text-muted-foreground'
+ className='text-foreground/70'
```

Color contrast reference table (on white `#ffffff`):

| Lightness (HSL L) | Approx hex | Approx ratio |
|---|---|---|
| 60% | #999999 | 2.8:1 |
| 55% | #8c8c8c | 3.3:1 |
| 50% | #808080 | 3.9:1 |
| 45% | #737373 | 4.5:1 ✓ |
| 40% | #666666 | 5.3:1 ✓ |
| 35% | #595959 | 6.3:1 ✓ |
| 30% | #4d4d4d | 7.5:1 ✓ |

### 2. heading-order

**Parse step — relevant fields:**
- `nodes[].html` — e.g. `<h3>Sub-section</h3>`
- `nodes[].target` — CSS selector
- `nodes[].failureSummary` — will mention skipped level

**Locate strategy:**
1. Search for the heading text in `.tsx` files and `.mdx` files in `content/`
2. Read the page component that contains the heading (walk up the `app/` directory structure based on route context)
3. Identify all headings on that page (h1, h2, h3, h4, h5, h6)

**Analyze strategy:**
1. Build the heading hierarchy for the page
2. Check for skipped levels (e.g. h1 → h3 without h2)
3. Check for duplicate h1 or missing h1
4. If the heading comes from MDX content (e.g. `## Title`), note that MDX content uses markdown heading syntax which is rendered by `next-mdx-remote`

**Fix format:**
For TSX files:
```diff
- <h3>Sub-section</h3>
+ <h2>Sub-section</h2>
```

For MDX content (in `content/` directory):
```diff
- ### Sub-section
+ ## Sub-section
```

### 3. image-alt

**Parse step — relevant fields:**
- `nodes[].html` — e.g. `<img src="photo.jpg">` or `<Image src="..." />`
- `nodes[].target` — CSS selector

**Locate strategy:**
1. Search for the `src` value or surrounding text content in `.tsx` and `.mdx` files
2. Handle three patterns:
   - Direct `<img>` tag — rare in this codebase except through MDX
   - `<Image>` from `next/image` — used in components and pages
   - `<MDXImage>` component — used in MDX content rendering (see `components/mdx-image.tsx`, `app/posts/[slug]/page.tsx:26-28`, `app/experiences/[slug]/page.tsx:19-24`)

**Analyze strategy:**
1. Check if the element has an `alt` attribute
2. If `<Image>` has `alt={title || ''}` (empty string fallback), flag that the image is missing descriptive alt text even though it passes the validator
3. If `<MDXImage>` is missing an `alt` prop, trace back to the MDX file's `![alt](src)` markdown syntax — the alt text must be added in the `.mdx` content file
4. For decorative images that genuinely should have `alt=""`, suggest adding a comment and empty alt

**Fix format:**
For `<Image>` in TSX:
```diff
- <Image src={image} alt={title || ''} />
+ <Image src={image} alt={title ? `${title} cover image` : 'Decorative cover image'} />
```

For `<img>` in TSX:
```diff
- <img src={src} />
+ <img src={src} alt="Description of the image" />
```

For MDX files (`content/posts/*.mdx`, `content/experiences/*.mdx`):
```diff
- ![][image]
+ ![Photo of the project dashboard][image]
```

### 4. label

**Parse step — relevant fields:**
- `nodes[].html` — e.g. `<input id="name" type="text">`
- `nodes[].target` — CSS selector

**Locate strategy:**
1. Search for the element `id` or `placeholder` text in `.tsx` files
2. Identify the form control and its parent component

**Analyze strategy:**
1. Check if the input has `id` — if so, search for a matching `<label htmlFor="...">` in the same file or nearby
2. Check if the input has `aria-label`
3. If the input uses the shared `<Input>` component (from `components/ui/input.tsx`), the label must be in the parent component
4. If `<Input>` is used without an `id` and without `aria-label`, the parent needs fixing

**Fix format:**
For missing `<label>`:
```diff
+ <label htmlFor="name" className="sr-only">Name</label>
  <Input id="name" />
```

For missing `aria-label` on the `<Input>` component:
```diff
- <Input placeholder="Search..." />
+ <Input placeholder="Search..." aria-label="Search" />
```

### 5. button-name

**Parse step — relevant fields:**
- `nodes[].html` — e.g. `<button><SomeIcon /></button>`
- `nodes[].target` — CSS selector

**Locate strategy:**
1. Search for the HTML content (icon name, surrounding text) in `.tsx` files
2. Identify whether it's a `<button>` element or the `<Button>` component from `components/ui/button.tsx`

**Analyze strategy:**
1. Check if the button has visible text content
2. Check for `aria-label` attribute
3. Check for `sr-only` child text (screen-reader-only visible text)
4. If the button is icon-only (like `<Button size="icon">`), it must have `aria-label`
5. If `aria-label` exists but has a typo (like "Increace" instead of "Increase"), flag it

**Fix format:**
For missing `aria-label`:
```diff
- <Button size="icon"><XIcon /></Button>
+ <Button size="icon" aria-label="Close"><XIcon aria-hidden="true" /></Button>
```

For typo in `aria-label`:
```diff
- aria-label="Increace count"
+ aria-label="Increase count"
```

For icon buttons with visible text using `sr-only`:
```diff
  <Button size="icon" aria-label="Close">
    <XIcon aria-hidden="true" />
+   <span className="sr-only">Close</span>
  </Button>
```

## Report template

Each violation gets a dedicated section in the output. When multiple violations are provided, concatenate them under a single `## Fix Plan` heading.

```markdown
## Fix Plan: {rule-id}

### Violation Details
- **Impact**: {impact}
- **Element**: `{html}`
- **Selector**: `{target}`
- **Failure Summary**: {failureSummary}
{violation-specific data like contrast ratio, fg/bg colors, font size, etc.}

### Root Cause
{explanation of why this fails — the CSS variable, missing attribute, or oversight}

### Fix
{description of the fix}

{code block with the specific diff}

{any additional notes e.g. dark mode impact for color-contrast}

### Verification
```bash
npx playwright test accessibility-tests/accessibility.spec.ts
```
```

## Verification

After presenting the fix plan, tell the user:
- To apply the changes, they can ask you to edit the files
- After edits, re-run: `npx playwright test accessibility-tests/accessibility.spec.ts`
- If new pages/components were added, they should also add a new test section in `tests/e2e/accessibility-tests/accessibility.spec.ts`
